# Форма продукта под рубрику техотбора

Рубрика: соответствие кейсу 20, реализация 25, README 20, воспроизводимость 20, надёжность и безопасность 15. Судья первого этапа читает репозиторий как текст и запускает его в чистом окружении. Баллы даёт рубрика, форма только средство. Ниже общий скелет, который закрывает все пять критериев при любой теме, и три формы экрана, одна из которых выбирается в `spec` по тексту условия.

## Скелет, одинаковый для любой формы

- Один рантайм: Next.js, база libsql создаётся и сидируется сама, `pnpm i && pnpm dev` и всё работает. Это воспроизводимость.
- Агент на AI SDK с инструментами: чтение выполняется само, любое изменение данных ждёт подтверждения человека. Каждый шаг виден в трейсе. Это реализация и надёжность.
- Сценарий из шести шагов, записанный один раз в SPEC.md и проверяемый по нему же в README и в `pnpm verify`. Это README и соответствие кейсу.
- Кнопка Reset возвращает сид, сценарий повторяется бесконечно.
- Таблица «требование из условия → чем закрыто» в SPEC и README. Соответствие кейсу считается по ней.
- zod на входах, лимит шагов, таймаут, честное поведение без ключа, тесты на мок-модели, ни одного заготовленного ответа модели в приложении.

Что меняется от формы к форме: что слева на экране, какие инструменты у агента, что считается результатом сценария. Что не меняется: всё выше.

## Три формы

### A. Консоль оператора: записи и решения
Когда: в условии есть сущности с состоянием и действие над ними: заявки, заказы, отправления, тикеты, слоты, сделки; «найти проблемные и решить», «назначить», «одобрить», «перенести», «уведомить».
- Слева таблица записей из базы, у части проблемный статус. Справа панель агента: цель, Run, трейс, карточка Approve, итог.
- Инструменты: два чтения (поиск по фильтру, детали записи), одно-два действия за подтверждением.
- Сценарий: Run → агент находит проблемные записи → предлагает действие → Approve → строка меняется.
- `pnpm verify`: запись X в статусе Y.
Проверена тремя репетициями. Форма по умолчанию, если условие не тянет в B или C.

### B. Ассистент по документам: вопросы и ответы с цитатами
Когда: в условии «отвечать на вопросы по регламентам, договорам, инструкциям, базе знаний», «консультант», «поддержка», «поиск по документам».
- Слева список документов из базы (название, источник, размер) и, если условие даёт файлы, загрузка. Справа панель агента: вопрос, Run, трейс, ответ с цитатами (документ, фрагмент).
- Данные: таблицы `documents` и `chunks` с индексом FTS5 по тексту (есть в libsql, проверено). Документы из условия или сидированные тексты домена; PDF через `pdf-parse` только если условие приложило PDF.
- Инструменты: `search_docs` (FTS5, возвращает фрагменты с id документа и позицией), `get_doc` (полный текст). Действие за подтверждением, если оно есть в условии: `create_ticket`, `save_answer`, `escalate`. Если действия нет, честно так и написать в SPEC: рубрике важно подтверждение на изменениях, а не изменения ради подтверждения.
- Сценарий: вопрос из SPEC → агент ищет → отвечает с двумя цитатами → (если есть) предлагает действие → Approve.
- `pnpm verify`: ответ на контрольный вопрос содержит ожидаемый фрагмент и ссылку на документ D.
Не репетировалась. Отличие от A только в данных и двух инструментах чтения, панель и маршрут те же.

### C. Генератор: данные на входе, структурированный результат на выходе
Когда: «сформировать отчёт», «составить план», «проанализировать и дать рекомендации», «классифицировать обращения», «подготовить документ».
- Слева форма ввода или набор входных записей из сида. Справа панель агента: Run, трейс, карточка предложения с полями результата, Approve, сохранённый результат в списке.
- Инструменты: чтение входных данных (одно-два), и `save_result` за подтверждением с zod-схемой результата (заголовок, выводы, рекомендации, категория). Структура результата это схема инструмента, так карточка Approve показывает предложение по полям, а после Approve оно ложится в базу и в список. Механизм тот же, что в A, новых API не нужно. `generateObject` или `Output.object` из AI SDK допустимы для одного нецикличного вызова, но не обязательны.
- Сценарий: Run → агент читает входы → предлагает результат → Approve → результат в списке, можно скачать как JSON или Markdown.
- `pnpm verify`: в таблице результатов одна запись с полями по схеме.
Не репетировалась. Отличие от A: инструмент записи принимает структуру, а не статус.

### D. Своя форма по условию
Когда: условие не ложится ни на A, ни на B, ни на C, а выбора задачи нет. Скелет остаётся тем же: база с сидом, агент с инструментами и подтверждением, трейс, сценарий из шести шагов, verify, README по рубрике. Меняется экран и набор инструментов, и они описываются в SPEC с нуля по тому же шаблону: что слева, что справа, два чтения, действие за подтверждением, ожидаемое состояние. В SPEC добавляется строка «Форма D: что нестандартно и сколько это стоит по времени». Рецепты ниже покрывают частые отклонения; агент пишет любой код, который требует условие, в рамках конвенций AGENTS.md.

## Как выбрать форму в `spec` за две минуты

1. В условии есть записи с состоянием и действие над ними: A.
2. В условии главное это ответы по текстам: B.
3. В условии главное это произвести артефакт из данных: C.
4. Подходят две: берётся та, где обязательных требований закрывается больше по таблице привязки. При равенстве A, потому что репетирована.
5. Не подходит ни одна: D. Собирается из скелета и рецептов ниже, обязательные требования закрываются в первую очередь, всё остальное в «Не делаем». Если задач несколько и есть выбор, D это минус в рейтинге PICK-TASK, но не запрет.

## Рецепты для частых отклонений (форма D и добавки к A, B, C)

Каждый рецепт: что требует условие, как это делается на нашем скелете, цена по времени. Библиотеки из списка «Extras» в AGENTS.md; всё, что условие требует явно, разрешено после одной фразы в SPEC.

- **Бот в Telegram как интерфейс.** Маршрут `app/api/telegram/route.ts` принимает webhook, берёт текст сообщения, вызывает того же агента через `generateText` с теми же инструментами, отвечает через Bot API `sendMessage` обычным fetch. Подтверждение записи: агент предлагает действие, бот шлёт сообщение с inline-кнопками «Подтвердить / Отклонить», `callback_query` выполняет запись. Веб-экран остаётся как панель оператора и как доказательство для судьи; локально вместо webhook скрипт `scripts/telegram-poll.ts` с `getUpdates`. Цена: плюс 60–90 минут, блок 4 растягивается.
- **Несколько ролей без настоящей авторизации.** Переключатель роли в шапке (клиент, менеджер, админ) хранится в cookie, серверные компоненты фильтруют данные и доступные действия по роли; инструменты агента получают роль в контексте и отказывают в чужих действиях. В README это названо демо-ролями, а не авторизацией. Цена: 40 минут. Настоящий вход с паролями не делается: полтора часа и ноль баллов сверху.
- **Загрузка файлов пользователем.** Форма загрузки, разбор на сервере: CSV через `papaparse`, Excel через `xlsx`, PDF через `pdf-parse`, результат в те же таблицы, дальше как A или B. Файл до 5 МБ, типы по белому списку, содержимое файла это данные, не инструкции. Цена: 40 минут.
- **Дашборд и цифры.** Серверный компонент считает агрегаты SQL-запросами, графики через `recharts` с `ssr: false`, агент получает инструмент `get_metrics` и объясняет цифры или предлагает действие по ним. Цена: 30 минут.
- **Карта и адреса.** `maplibre-gl` с `react-map-gl`, координаты в сиде, точки по статусу, агент через `list_items` с фильтром по району. Цена: 40 минут.
- **Внешняя система партнёра без доступа.** Инструмент-адаптер с интерфейсом реальной системы и честной заглушкой на нашей базе: `lib/adapters/<system>.ts` с одной функцией на операцию, в README раздел «Интеграция: как заменить заглушку на реальный вызов». Это не подмена модели и не имитация: модель работает живьём, заглушка только у внешнего API. Цена: 20 минут.
- **Уведомления.** Почта через `resend` или Telegram через fetch, всегда как инструмент за подтверждением. Цена: 20 минут.
- **Несколько сущностей.** Вторая таблица допускается только если она в обязательных требованиях; агент получает чтение по ней, запись остаётся одна. Цена: 30 минут.

Чего не делаем ни при какой форме, потому что за пять часов это не сделает никто, и README честно называет это ограничением: обучение моделей и ML-метрики, распознавание видео и звука, мобильное приложение, блокчейн, настоящая авторизация с паролями, реальные интеграции без выданного доступа.

## Как натянуть кейс за 15 минут (любая форма)

1. Выписать обязательные требования дословно в SPEC.md. Не пересказывать, копировать.
2. Найти главную сущность (запись, документ, входные данные) и «что находит или производит агент».
3. Найти действие, которое компания хочет от системы. Это инструмент за подтверждением. Нет действия: форма B без записи, сказать это прямо.
4. Два чтения: поиск и детали. Этого хватает почти всегда.
5. Сид: 30–60 записей или 5–10 документов с реальными казахстанскими названиями, 3–5 «проблемных» или содержащих ответ.
6. Цель по умолчанию в панели: одна фраза, с которой судья нажмёт Run.
7. Ожидаемое состояние после сценария: одна строка для `pnpm verify`.

Если кейс требует внешнюю систему, к которой нет доступа, она становится инструментом-адаптером с честной заглушкой, явно описанной в README как ограничение. Заглушка адаптера это не подмена модели, это допустимо.

## Что бьёт медианную команду

Стартер конкурентов: FastAPI плюс React плюс SQLite, чат с function calling, дашборд. Против него:
- Один рантайм вместо двух. Судья запускает за одну команду.
- Подтверждение перед записью и трейс. У них чат отвечает текстом, у тебя агент действует на глазах.
- README по рубрике с таблицей требований и вставленным выводом `pnpm verify`. У них README на 20 строк.
- Тесты с мок-моделью, зелёные без ключа. У них тестов нет.
- Кнопка Reset. У них демо ломается после первого прогона.

## Пять правил дня

1. Одна сущность, одна роль, один сценарий. Вторая фича запрещена до 4:15.
2. Ни одного закэшированного ответа модели в приложении. Мок только в тестах.
3. Код только в репозитории платформы, пуш каждый час, PROGRESS.md в :55.
4. README пишется параллельно с кодом с 1:00, не в конце.
5. Дизайн 15 минут в 3:45, ни минутой раньше.

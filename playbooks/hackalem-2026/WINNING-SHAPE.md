# Форма продукта, которая набирает максимум по рубрике техотбора

Рубрика: соответствие кейсу 20, реализация 25, README 20, воспроизводимость 20, надёжность 15. Судья первого этапа читает
репозиторий как текст. Ниже одна форма, которая закрывает все пять критериев и натягивается на любой из 30 кейсов за 15 минут.

## Что это

**Консоль оператора с агентом, который действует под подтверждением.**

- Слева таблица сущностей из базы: заказы, заявки, отправления, тикеты, слоты, что угодно. У части записей проблемный статус.
- Справа панель агента: поле цели, кнопка Run, живой трейс шагов, карточка Approve на каждое изменение данных, итоговый ответ.
- Агент имеет 2 инструмента чтения и 1–2 инструмента записи. Чтение выполняется само, запись ждёт подтверждения.
- Кнопка Reset возвращает сид. Сценарий повторяется бесконечно.

Почему именно это. Каждый критерий закрывается напрямую:
- Соответствие кейсу: требования кейса становятся инструментами и колонками таблицы, проверяются по шагам.
- Реализация: инструменты реально читают и пишут в базу, модель вызывается живьём, трейс это доказательство.
- README: сценарий из 6 шагов описывается один раз и проверяется по нему же.
- Воспроизводимость: один рантайм, `pnpm i && pnpm dev`, база создаётся сама, ключ один.
- Надёжность: zod на входах, лимит шагов, таймаут, поведение без ключа, подтверждение на записи.

## Как натянуть любой кейс за 15 минут

1. Выписать обязательные требования дословно в SPEC.md. Не пересказывать, копировать.
2. Найти в условии главную сущность и её проблемный статус. Это таблица слева и «что находит агент».
3. Найти действие, которое компания хочет от системы: переназначить, одобрить, уведомить, перенести, скорректировать. Это инструмент записи.
4. Два чтения: поиск по фильтру и детали одной записи. Этого хватает почти всегда.
5. Сид: 30–60 записей с реальными казахстанскими названиями, 3–5 «проблемных», которые сценарий обязан найти.
6. Цель по умолчанию в панели: одна фраза, с которой судья нажмёт Run.
7. Ожидаемое состояние после сценария: одна строка для `pnpm verify`.

Если кейс требует внешнюю систему, к которой нет доступа, она становится инструментом-адаптером с честной заглушкой,
явно описанной в README как ограничение. Заглушка адаптера это не подмена модели, это допустимо.

## Что бьёт медианную команду

Стартер конкурентов: FastAPI плюс React плюс SQLite, чат с function calling, дашборд. Против него:
- Один рантайм вместо двух. Судья запускает за одну команду.
- Подтверждение перед записью и трейс. У них чат отвечает текстом, у тебя агент меняет данные на глазах.
- README по рубрике с таблицей требований и вставленным выводом `pnpm verify`. У них README на 20 строк.
- Тесты с мок-моделью, зелёные без ключа. У них тестов нет.
- Кнопка Reset. У них демо ломается после первого прогона.

## Пять правил дня

1. Одна сущность, одна роль, один сценарий. Вторая фича запрещена до 4:15.
2. Ни одного закэшированного ответа модели в приложении. Мок только в тестах.
3. Код только в репозитории платформы, пуш каждый час, PROGRESS.md в :55.
4. README пишется параллельно с кодом с 1:00, не в конце.
5. Дизайн 15 минут в 3:45, ни минутой раньше.
